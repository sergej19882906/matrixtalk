## Критичные ошибки: исправить прежде новых функций

### 1. P1 — Ключи шифрованных вложений доступны homeserver

**Файл:** `shared/src/commonMain/kotlin/com/matrix/messenger/data/repository/MatrixRepositoryImpl.kt:803–815, 860, 893–927, 1154–1165, 2007–2027`.

Байты медиа шифруются, но событие с `EncryptedFile.key` отправляется напрямую `api.room.sendMessageEvent`. Этот API сериализует и отправляет переданный контент; E2EE события выполняется другим слоем Trixnity. Поэтому шифрование файла не скрывает его от сервера, которому передан ключ. Аналогично direct-send обходят событийное шифрование для опросов, голосов и геолокации.

Кроме того, `fileInfo?.let { null } ?: mxc` всегда возвращает `mxc`: контент содержит одновременно `url` и `file` вместо правильного выбора.

**Исправление:** отдельный проверенный путь шифрования room event после upload; зашифрованная комната должна отправлять `m.room.encrypted`, без открытого ключа/исходного контента на проводе. Ошибка загрузки/определения шифрования не должна незаметно переключать отправку на plaintext.

**Регрессия:** проверить тип и содержимое реально отправляемого события для текста, файла, голоса, стикера, опроса, геолокации.

### 2. P1 — UnifiedPush не подключён корректно

**Файлы:** `app/src/main/AndroidManifest.xml:122–124`; `shared/src/androidMain/kotlin/com/matrix/messenger/service/RegisterPusherWorker.kt:62–71`.

Receiver объявлен `exported=false`, поэтому внешнему приложению-дистрибьютору запрещены broadcast-события. Позиционные аргументы `SetPushers.Request` перепутаны: по реальному API 4.9.2 `appDisplayName, appId, append, data, deviceDisplayName, kind, lang, profileTag, pushkey`. Текущий код передаёт `appId=endpoint`, `kind="MatrixTalk Android"`, `pushkey="false"`, `append=true`.

**Исправление:** контракт безопасного доступного distributor receiver, именованные аргументы, `kind="http"`, правильные appId/pushkey и Matrix-совместимый push gateway. Просто указать произвольный ntfy topic как Matrix gateway недостаточно для доказательства совместимости.

**Регрессия:** roundtrip endpoint → HTTP-pusher JSON → реальный push → уведомление на закрытом клиенте.

### 3. P1 — Кнопка выхода в настройках не завершает сессию

**Файлы:** `ui/settings/SettingsScreen.kt:485–496`; `ui/navigation/AppNavigation.kt:212–220`; `ui/settings/SettingsViewModel.kt:219–222` (пути относительны `shared/src/commonMain/kotlin/com/matrix/messenger/`).

Кнопка вызывает только navigation callback. Реализованный метод ViewModel `logout()` не вызван. Токен/клиент остаются активными, при перезапуске возможен автовход.

**Исправление:** дождаться успешного repository logout и лишь затем сбрасывать навигацию; ошибки показывать пользователю. Проверить фоновые задания и плееры при выходе.

### 4. P1 — PIN-защита заявлена, но настройка недоступна

**Файлы:** `ui/settings/SettingsScreen.kt:85–99`; `ui/settings/SettingsViewModel.kt:79`; `ui/navigation/AppNavigation.kt:45–50`; `ui/settings/PinLockScreen.kt:44–54`.

`pinDialog` нигде не становится true. `pinEnabled = runCatching { ... } != null` сравнивает объект Result с null и всегда сообщает true. Гейт запоминает хэш/разблокировку один раз, не блокирует при возврате из фона; неправильные попытки не имеют задержки/лимита. Хэш четырёхзначного PIN сам по себе не даёт стойкого шифрования хранилища.

**Исправление:** реально подключить настройку, использовать nullable result, проверять старый PIN для смены/отключения, lifecycle relock, ограничение попыток. Чётко отделить UI-lock от шифрования локальных данных.

### 5. P1 — Сигналинг другого звонка воздействует на текущий

**Файлы:** `shared/src/commonMain/kotlin/com/matrix/messenger/data/repository/CallRepository.kt:48–60`; Android `call/AndroidWebRtcEngine.kt:117–143`; Desktop `call/DesktopWebRtcEngine.kt:127–151`.

Answer/candidates/hangup/reject не сверяются с активными roomId/callId; движки также не обеспечивают эту проверку. Hangup другого звонка может завершить текущий.

**Исправление:** проверка room/call/peer до обработки каждого сигнального события, защита движка от чужого callId.

### 6. P1 — Голосовое отправляется с неверным внешним типом события

**Файл:** `shared/src/commonMain/kotlin/com/matrix/messenger/data/repository/MatrixRepositoryImpl.kt:842–860, 2141–2173`.

`msgtype="m.audio"` должен находиться внутри `m.room.message`, но текущая отправка выставляет также внешний event type `m.audio`. Своя специальная Unknown-ветка маскирует ошибку; Element может скрыть такое событие. Ранний return этой ветки пропускает заполнение media-кэшей; persistent fallback в resolveMediaFile обрабатывает только FileBased-контент.

**Исправление:** стандартный room-message envelope, правильная MSC-структура waveform/voice marker, единый media resolver для всех контентов. Проверять после холодного запуска.

### 7. P1 — Режим уведомлений аккаунта меняет неверное правило

**Файл:** `shared/src/commonMain/kotlin/com/matrix/messenger/data/repository/MatrixRepositoryImpl.kt:2442–2456, 2553–2565`.

Используется `.m.rule.room_message` вместо `.m.rule.message`. Даже после замены одной константы отдельные DM/encrypted underride-правила будут продолжать уведомлять в режиме «Упоминания».

**Исправление:** работать со всем релевантным набором стандартных правил, показывать ошибки API, не считать локальное переключение подтверждением серверного результата.

### 11. P1 — Desktop пишет не WAV, а сырой PCM с расширением .wav

### 12. P2 — Контролируемый плеер не распознаёт extensionless голосовые

**Файлы:** `shared/src/commonMain/kotlin/com/matrix/messenger/ui/chat/ChatViewModel.kt:491–493`; `data/repository/MatrixRepositoryImpl.kt:699–702`; Desktop `platform/AudioDecode.kt:27–35`.

Имя файла берётся из текста сообщения, а декодер выбирается только по расширению. «Голосовое сообщение» без расширения теряет встроенные pause/seek/progress.

**Исправление:** определение контейнера по байтам/MIME, корректное временное имя файла.

### 13. P2 — Гонки при смене/подготовке аудио

**Файлы:** Desktop `platform/VoicePlayback.desktop.kt:60–65, 92–119, 133–148, 191–193`; Android `platform/VoicePlayback.android.kt:53–79, 91–100`.

Desktop не дожидается старого writer thread, общий stopped сбрасывается новым запуском; старый поток может закрыть новую line. На естественном завершении отсутствует drain, хвост буфера обрезается. Android сохраняет player лишь в onPrepared: stop во время подготовки не освобождает его, устаревший callback может запустить вторую дорожку.

**Исправление:** владение отдельной playback session/generation, отмена и освобождение конкретного player, корректная позиция проигрывания/буферизация и completion.

## Фон, настройки и сервер

### 21. P2 — Worker игнорирует in-app настройки и отмечает события слишком рано

**Файлы:** `shared/src/androidMain/kotlin/com/matrix/messenger/service/MessageNotificationWorker.kt:39–42, 69–95`; `app/src/main/java/com/matrix/messenger/push/MatrixtalkPushReceiver.kt:18–26`; Android `platform/Platform.kt:180–188`.

Worker проверяет только OS permission/unread count, не переключатель приложения, mute/mentions. Timestamp записывается до появления usable decrypted content, поэтому уведомление может потеряться навсегда. Отключение отменяет periodic worker, но не push-triggered work.

**Исправление:** фильтрация предпочтений внутри worker, ожидание расшифровки, dedup после обработки; удалить pusher/отменить pending work при выключении/выходе.

### 22. P2 — Кириллические ключевые слова перезаписывают друг друга

**Файл:** `shared/src/commonMain/kotlin/com/matrix/messenger/data/repository/MatrixRepositoryImpl.kt:2464–2477`.

Rule ID заменяет каждый non-ASCII символ на underscore. «работа» и «привет» получают один ID.

**Исправление:** collision-resistant ID (нормализованный UTF-8 digest/encoding), тест на несколько разных слов.

### 23. P2 — SessionStore молча теряет сохранение

**Файл:** `shared/src/commonMain/kotlin/com/matrix/messenger/data/repository/SessionStore.kt:81–85, 100–103, 139–175, 181–182`.

Cache обновляется до файловой записи, ошибка write подавляется. Многие новые mutators не используют mutex. Поэтому UI сообщает success, а после перезапуска возвращаются старые значения; concurrent update может потерять настройки.

**Исправление:** атомарная запись, cache после success, единая блокировка read-modify-write, propagation errors. Тесты должны сбрасывать cache и моделировать write failure.

### 24. P2 — Новые bridge-контейнеры не подключены к Synapse

**Файлы:** `docker-compose.bridges.yml:10–14`; `docker/synapse/configure.py:45–53`.

Сервисы восьми мостов объявлены, но registration mounts и scanner включают только Telegram/WhatsApp/Signal. Для остальных auto-registration отсутствует.

**Исправление:** согласованные mounts/scanner/registration generation, сохранять вручную настроенные appservices, контейнерные startup tests. Docker build success не проверяет старт и регистрацию моста.

Дополнительное место для проверки server-side: `docker/ntfy/server.yml:5` использует `cache_file` вместо стандартного `cache-file`; полный запуск ntfy/новых entrypoint-скриптов этим аудитом не проверен.

## Рекомендуемый порядок работ

1. E2EE wire encryption + правильный voice envelope; logout/PIN; UnifiedPush registration и receiver; callId filtering.
2. UI layout/search, typed call mapping, media caches, валидная запись и безопасные плееры.
3. Poll end, bridge state, thread actions, Spaces join/pagination, notification preferences/persistence.
4. Серверные smoke/integration tests и корректировка README/RELEASE_NOTES под фактические возможности.

До подтверждения первых пунктов не следует считать заявленное E2EE-медиа, мгновенный push и PIN-lock завершёнными функциями.

## Что не было признано ошибкой без доказательств

- Отсутствие явного Realm clear в forceLogout само по себе не доказывает восстановление отозванного токена: стандартный Trixnity M_UNKNOWN_TOKEN handler очищает token в persisted account.
- Sealed RoomMessageEventContent не означает, что невозможно подключить custom message serializer/waveform: предыдущий вывод «заблокировано SDK» был слишком категоричным.
- Stereo Opus frame-size suspicion не повышен до дефекта без воспроизводимого invalid packet/output scenario.
- SDK upgrade/QR/cross-signing bootstrap требуют отдельной оценки API, их отсутствие не является доказанной невозможностью реализации.
